# Project Wing Agent Guide

This file defines repository-wide working rules for Project Wing. A nested `AGENTS.md` applies in addition to this file and takes precedence for files in its directory. The `AGENTS.md` files generated by Next.js under individual apps are framework notices; do not remove or hand-edit their generated blocks.

The current user request has the highest priority. This guide defines normative repository constraints; executable scripts, package manifests, tests, and workflow files define current repository behavior. When descriptive prose and executable behavior disagree, verify the executable source and update the stale prose rather than inventing a compromise. A script's existence does not by itself authorize a remote, destructive, or out-of-scope action.

Do not claim that a command, check, PR, workflow, deployment, or browser flow passed without current evidence.

## Implementation and UI Ownership

Keep domain code grouped by feature. Colocate JavaScript and TypeScript tests with the code they cover using `*.test.*` or `*.spec.*`.

Use TypeScript for JavaScript workspaces. Native Desktop Agent code follows its existing .NET, React Native, Objective-C/C++, PowerShell, and shell toolchains. Use explicit types at API and shared-contract boundaries. Never return sensitive fields such as `passwordHash`.

Cross-application behavior and visual contracts belong in `packages/ui`; genuinely application-specific adaptations stay with the owning application. Do not duplicate a shared primitive across applications.

Reusable and shared component copy requires semantic review so English fallbacks and ownership remain correct.

Display-only headings that restate a route, selected item, or nearby control are discouraged. A title should identify a task, object, or state that is otherwise unclear.

## Testing and Completion Evidence

JavaScript and TypeScript workspaces use Vitest. Tests should protect business behavior, permissions, workflow transitions, persistence boundaries, errors, and accessibility contracts. Interaction value and business relevance remain review judgments.

For routine work, run targeted workspace tests. Reserve the root `test` command for cross-cutting changes, shared contracts, root configuration, merge-readiness checks, and explicit requests.

For UI and user-workflow changes, automated tests are not sufficient. Exercise the modified flow in a real running application and capture a screenshot or equivalent visual artifact. Use a backend-attached browser-login deployment when the flow depends on authentication, API state, storage, project data, or Desktop Agent behavior.

Desktop Agent failure tests must explicitly isolate both StateRoot and CacheRoot, use independently allocated ports and synthetic files, and disable file launch. Do not fault-inject against the installed Agent, Office or user caches as a substitute for an isolated test. Installed-app acceptance requires explicit task scope and protection of non-test work. The native release workflow runs real isolated Manager recovery and file-safety gates in addition to static delivery-contract checks.

Completion reports must state the exact commands run, their results, the interactive path and environment for UI work, and anything that was not run.

## CI and Delivery Model

The current workflow set has no `pr-validation.yml` or automatic pull-request validation lane. Pre-merge confidence requires local validation, targeted review, checking any reported PR status checks, and honest handoff evidence; absence of checks is not a passing validation result.

After a change reaches `main`, `.github/workflows/build.yml` builds or reuses an immutable image generation. A successful main-branch Build automatically triggers `.github/workflows/deploy.yml`, which activates the verified full-stack generation through the reusable deployment workflow. Manual recovery deployment is also available; do not manually dispatch it without authorization. The Desktop Agent uses its separate native workflow. Workflow files and `scripts/ci/` define current delivery behavior; descriptive deployment documentation may lag behind them.

Development business ingress uses dual static-file Traefik Edge nodes behind one private Alibaba Cloud HaVip. NetBird distributes that HaVip through both application hosts; the Hong Kong gateway remains control-plane-only. Edge promotion is standby-first, commits one shared generation on both nodes, and must fail closed on conflicting state.

Treat these as distinct states and report them separately:

1. local validation passed;
2. PR pushed or merged;
3. GitHub workflow started;
4. validation passed;
5. artifacts were built and published;
6. remote deployment and verification completed.

A successful Validate job is not proof that deployment completed.

## Worktrees, Commits, and Pull Requests

Use an isolated `.worktrees/` worktree and a dedicated branch for implementation work. Use one worktree per task, preserve unrelated dirty changes, and do not modify the shared `main` checkout directly.

PR titles should use concise Conventional Commit syntax. Do not push, merge, rewrite history, or delete a worktree unless the user has authorized that remote or destructive action.

PRs should summarize affected modules, validation evidence, UI screenshots and interactive paths where applicable, and migration or deployment impact.

## Concurrent Changes and Conflict Resolution

Treat the current target branch as the integration baseline, especially for shared UI, global styles, contracts, migrations, CI, and tests.

- Preserve the functional and presentation behavior contributed by both sides of a conflict when they are compatible.
- Never resolve shared or high-churn files with a blanket ours/theirs choice.
- Do not replace established shared grids, preview infrastructure, form shells, dialogs, or layout primitives with stale branch-local alternatives.
- Do not weaken assertions or refresh snapshots merely to make a regression disappear.
- Stop and report ambiguity before resolving conflicts in global CSS, shared UI infrastructure, public contracts, schema migrations, or CI configuration.
- Run focused validation for both sides of a reconciliation and describe any behavior intentionally removed.

## Security, Persistence, and Prisma

Never hard-code credentials. Use parameterized data access through Prisma or the appropriate existing adapter. Persisted business mutations through the API must emit an audit log when the domain requires traceability; whether a mutation requires that traceability is a domain-review decision.

Do not describe Prisma migrations as inherently zero-downtime. Assess locks, destructive changes, backfills, compatibility, and rollback for each migration.

## Maintaining This Guide

Update this file when workspace boundaries, semantic ownership, validation expectations, CI behavior, or deployment topology change.
